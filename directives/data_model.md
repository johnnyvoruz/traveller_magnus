# Data model — objects, pointers, manifests

**Status:** ADOPTED 2026-10-02 (revised the same day: platform-owned generation, roles,
search, retention). Drizzle schemas in `apps/api/src/db/schema.ts` (D1) and
`apps/api/src/universe/schema.ts` (Durable Object SQLite) are written from this file and must
match it. Ids are `text` ULIDs unless noted; timestamps are ISO-8601 text; hashes are lowercase
hex sha256 of the object bytes.

---

## 1. Objects (R2)

An object is an immutable blob named by its hash. JSON objects use the stable serialization
(`packages/shared/stable.ts`: sorted keys, **no whitespace** from truth v2 on, explicit non-finite
numbers) so identical content always has the same hash. Truth v1 was built pretty-printed (two-space
indent, about 85 KB a tree against 50 KB compact) and is not released; changing the serialisation
changes every hash, which is why it was done before any universe pinned a version.

| Where | Key | Contents |
|---|---|---|
| public bucket | `objects/<hash>` | truth system trees; package contents; anything published |
| private bucket | `u/<universeId>/objects/<hash>` | a builder's trees, images, snapshot bodies |

Object kinds:

- `tree` — one hex's full state after generation or editing: the `HexState` document. The
  platform validates its envelope (`kind`, `engineVersion`, `derivation`, `summary` projection,
  size) and treats the engine-owned body as a versioned document; the engine package owns the
  body's shape and the golden tests pin it.
- `snapshot` — a universe manifest (§4).
- `package-content` — an overlay subset (§7).
- images — `image/webp`; the asset id is the hash.

Publishing copies private objects to the public bucket under the same hash. A weekly cron
marks every hash referenced by truth indexes, universe rows, history rows, snapshot manifests
and package manifests, and sweeps the rest after a 30-day grace period.

## 2. Catalogue (D1)

Identity tables are **owned by better-auth** and generated by its CLI into the Drizzle schema:
`user` (with the `admin` plugin's `role`, `banned`, `banReason`, `banExpires`), `session`,
`account` (one row per linked OAuth provider), `verification`. We add nothing to them and never
write them directly; `role` values are `user`, `reviewer`, `admin`. Every `owner_id`,
`author_id`, `actor_id`, `reviewer_id` and `reporter_id` below references `user.id`. A `profile`
table of ours holds what the product needs beyond identity:

```sql
profile          (user_id PK FK user.id, handle UNIQUE, display_name, avatar_url, created_at, last_seen_at)

universes        (id PK, owner_id FK, name, slug, truth_version NULL, engine_version, edition_default,
                  created_at, updated_at, deleted_at NULL, purge_after NULL,
                  hex_override_count INT, object_bytes INT, last_snapshot_at NULL)

truth_versions   (version PK, engine_version, milieu, seed, settings JSON, sectors JSON,   -- the exact build inputs
                  state ('building'|'released'|'withdrawn'), started_at, released_at NULL, notes,
                  manifest_hash NULL, sectors_total INT, sectors_done INT, sectors_failed JSON)
truth_build_sectors (version, sector_slug, state ('queued'|'building'|'done'|'failed'), systems INT, built INT, partial INT,
                  index_hash NULL, error NULL, updated_at, PK(version, sector_slug))   -- sectors_done = COUNT(state='done')
truth_systems    (version, sector_slug, hex, name, uwp, allegiance, zone, tree_hash NULL, partial NULL, PK(version, sector_slug, hex))
truth_systems_fts  FTS5 virtual table over truth_systems(name, hex, uwp, sector_slug) content-synced by triggers

packages         (id PK, author_id FK, kind, title, slug UNIQUE, description, tags JSON, edition,
                  truth_version, engine_version, latest_version INT, installs INT,
                  created_at, updated_at, hidden INT, takedown_reason NULL, takedown_by NULL)
package_versions (package_id FK, version INT, manifest_hash, content_hash, bytes INT, hex_count INT,
                  record_count INT, created_at, PK(package_id, version))
package_installs (universe_id, package_id FK, version INT, installed_at, PK(universe_id, package_id))
player_publishes (id PK, universe_id, label, public_prefix, state ('building'|'live'|'revoked'), created_at, revoked_at NULL)
proposals        (id PK, package_id FK, version INT, target_truth_version, state ('open'|'accepted'|'rejected'),
                  reviewer_id NULL, reviewer_note, created_at, decided_at NULL)
reports          (id PK, package_id FK, reporter_id FK, reason, created_at, resolved_at NULL, resolved_by NULL)

```

Sessions, cookies and expiry are better-auth's, configured in `auth.ts` to a 30-day session
refreshed when used. `audit_log` is append-only.

## 3. One universe (Durable Object SQLite)

```sql
meta             (key PK, value)        -- schemaVersion, truthVersion, engineVersion, grid JSON, settings JSON
sectors          (sector_slug PK, display_name, x INT, y INT, source ('truth'|'own'))
hexes            (hex_key PK, sector_slug, local_hex, rev INT, updated_at, deleted INT,
                  base_hash NULL,       -- the truth tree hash this row overrides; NULL on own maps
                  tree_hash NULL,       -- the current tree object; NULL for a sector-scale-only edit
                  engine_version NULL,  -- engine that produced tree_hash
                  type, name, uwp, allegiance, zone, bases, trade_codes, pbg, ix,
                  summary JSON,         -- remaining sector-scale fields (t5Data, counts, notes…)
                  provenance JSON NULL) -- { packageId, version } when installed
hexes_fts        FTS5 over hexes(name, hex_key, uwp) content-synced by triggers
hex_history      (hex_key, rev, at, action, actor, tree_hash NULL, summary JSON, deleted INT, PK(hex_key, rev))
lists            (kind PK, rev INT, updated_at, payload JSON)
list_history     (kind, rev, at, action, payload_hash, PK(kind, rev))
snapshots        (id PK, at, label, trigger, manifest_hash, bytes INT)
jobs             (id PK, kind, state ('queued'|'running'|'done'|'failed'), total INT, done INT, failed INT,
                  failures JSON, created_at, finished_at NULL)

campaign_records (id PK, type, kind, name, summary, details, tags JSON, anchor JSON,
                  when_json JSON NULL, visibility, player_notes NULL, sheet JSON NULL, status JSON NULL,
                  images JSON NULL, provenance JSON NULL, rev INT, seq INT, created_at, updated_at, deleted INT)
campaign_links   (id PK, from_id, to_id, kind, role, link_order INT, since_json JSON NULL, until_json JSON NULL,
                  notes, visibility, provenance JSON NULL, rev INT, seq INT, created_at, updated_at, deleted INT)
campaign_journal (id PK, kind, title, body, when_json JSON NULL, real_date NULL, sequence INT NULL,
                  author, visibility, anchor JSON NULL, mentions JSON, rev INT, seq INT,
                  created_at, updated_at, deleted INT)
```

Rules of the `hexes` table:

- `hex_key` is `"<sector_slug>/<hhhh>"`. The legacy numeric slot is never identity. Position on
  the builder's grid is `sectors.x, y`; moving a sector changes no key.
- A hex that equals the truth has **no row**. A row exists when the builder changed something or
  the platform generated something for them.
- Every tree the platform generates is an object immediately; there are no deferred or virtual
  trees. The derivation that produced it is inside the tree document.
- `deleted = 1` is a tombstone hiding a truth hex or removing an own-map hex.
- `summary` plus the indexed columns are everything the map, search and trade match read; the
  tree is read when a dossier or the orbit view opens.
- `lists.kind` ∈ `routes, routeDefinitions, autoRouteCounter, borderDefinitions,
  hexBorderAssignments, borderPaths, regionDefinitions, regionPaths, allegianceDefinitions,
  hexAllegianceAssignments, sectorNames, subsectorNames, sectorReview, campaignTime,
  campaignSettings` — the overlay document keys, plus the party settings document and the
  campaign clock, whole payload per write.
- `campaignTime` is the campaign clock (`CampaignClock`: `{ days, rev }`). `days` is the
  orbit view's day count: finite, at least 0, and a fraction is the time of day. The row is
  absent until the first set. A change sends `{ days, baseRev }` (`baseRev` 0 the first
  time) and counts as one patch row. The stored `rev` starts at 1. A stale `baseRev` is a
  conflict whose `current` is the stored clock, or null when none is stored. Each successful
  change appends `list_history` (`kind` `campaignTime`, `rev`, `at`, `action` `set`,
  `payload_hash` the sha256 of the payload JSON). The current payload stays on `lists`.
- `hex_history` retention: last 50 revisions per hex and everything from the last 90 days;
  the weekly cron compacts older rows. Snapshots cover the long tail.
- Schema version 3 stores campaign rows in the Durable Object, including `campaign_journal`.
  `campaign_records_fts` and `campaign_assets` are not created yet.
- `when_json` is the record's `when` object (`{ start: { year, day }, end? }`), or null.
  `since_json` and `until_json` are the link's day objects. `link_order` is the link's `order`.
- `seq` is one counter per universe (`meta.campaignSeq`), stamped on every campaign write,
  including a journal entry. Tombstones stay in this slice. A restore writes the row with
  `deleted` 0 and `baseRev` equal to the stored `rev`. Deleting a record tombstones its links
  in that same write. A journal entry's stored `mentions` are `mentionsOf(body)`; the list on
  the change is not stored. Deleting a record leaves a journal entry anchored to it unchanged.
- `provenance` is nullable JSON on records and links: null, or
  `{ mode: 'copy' | 'shared', universeId, recordId, rev, at }` (`CampaignProvenance`).

Indexes: `hexes(sector_slug)`, `hex_history(at)`, `jobs(state)`, `campaign_records(seq)`,
`campaign_records(type)`, `campaign_links(seq)`, `campaign_links(from_id)`, `campaign_links(to_id)`,
`campaign_journal(seq)`, `campaign_journal(kind)`.

## 4. Snapshot manifest (object, kind `snapshot`)

```json
{ "kind": "snapshot", "universeId": "...", "at": "...", "label": "Before: Import Deneb",
  "truthVersion": "v1", "engineVersion": "1.2.0", "meta": { "grid": {}, "settings": {} },
  "sectors": [ { "sectorSlug": "Spinward_Marches", "x": 0, "y": 0, "source": "truth" } ],
  "hexes": { "Spinward_Marches/1910": { "rev": 7, "treeHash": "…", "baseHash": "…", "summary": {} },
             "Spinward_Marches/1912": { "rev": 1, "deleted": true } },
  "lists": { "routes": { "rev": 3, "payload": [] } },
  "campaign": { "recordsHash": "…", "linksHash": "…", "journalHash": "…" } }
```

A snapshot of a heavy builder's universe is a few hundred kilobytes because trees are hashes.
Restore = snapshot the current state, then replace rows from the manifest in one transaction.

## 5. Truth (public bucket)

```
truth/v<N>/manifest.json
truth/v<N>/overview.json               one 1,280-character string per sector (from v2)
truth/v<N>/sectors/<slug>/index.json
objects/<hash>                         system trees, shared by every version that points at them
```

`manifest.json`
```json
{ "truthVersion": "v1", "milieu": "M1105", "seed": "TravellerMagnus",
  "settings": { "generationPopMax": 20, "...": "all twelve keys" },
  "engineVersion": "1.0.0",
  "attribution": "Sector data from the Traveller Map (travellermap.com), used under Far Future Enterprises' Fair Use Policy. Traveller is a registered trademark of Far Future Enterprises.",
  "releasedAt": "set by the release endpoint, absent from a local build so two builds hash alike",
  "sectors": [ { "slug": "Spinward_Marches", "name": "Spinward Marches", "x": -4, "y": -1,
                 "tags": ["Official", "OTU"], "canonical": true,
                 "systems": 439, "built": 439, "partial": 0, "indexHash": "…" } ],
  "overviewHash": "…" }
```

`sectors/<slug>/index.json`
```json
{ "slug": "Spinward_Marches", "name": "Spinward Marches", "x": -4, "y": -1, "truthVersion": "v2",
  "tags": ["Official", "OTU"], "canonical": true, "systems": 439, "built": 439, "partial": 0,
  "hexes": { "1910": { "tree": "<hash>", "type": "SYSTEM_PRESENT", "name": "Regina", "uwp": "A788899-C",
                       "allegiance": "ImDd", "zone": "", "bases": "NS", "tradeCodes": [], "pbg": "703",
                       "ix": 4, "stars": "F7 V BD M3 V", "partial": null },
             "0914": { "tree": null, "type": "SYSTEM_PRESENT", "name": "Beauniture", "uwp": "C8858??-4",
                       "partial": "partial" } },
  "metadata": { "routes": [], "borders": [], "names": {} }, "wiki": { "1910": { } } }
```

`overview.json` (`{ truthVersion, sectors: [{ slug, name, x, y, tags, canonical, systems, cells }] }`)
lets the map draw every system at far zoom without fetching 512 indexes. `cells` has one
character per hex at position `(col - 1) * 40 + (row - 1)`: `.` for an empty hex, otherwise the
first character of the chart UWP as written (a literal `.` there is stored as `?`). Measured:
about 1.4 KB a sector, so roughly 720 KB for 512. It is written at release from the sector
indexes by `sectorOverview` (`packages/generation`), and the manifest carries its hash.

**Territories (from truth v3).** Each index carries `territories`: one entry per polity in the
sector, `{ id, name, color, allegianceCodes, hexes }`, where `hexes` is the sorted list of
`hhhh` the polity owns. They are computed at build time from the metadata XML's `<Border>`
paths by `sectorTerritories` (`packages/generation/src/territories.ts`), a line-for-line port
of the legacy flood fill that is held to the legacy code by twelve golden cases. The viewer
draws outlines and fills from the hex lists and never runs the fill. `metadata.allegiances`
(the XML's allegiance name table) arrives in the same version. Regions do not; they are a
later version.

An index entry is the chart row and nothing else: the fields the map draws, each stored once.
`stars` is the chart's Stars column as written. Truth v1 entries carried a `summary` that was a
second copy of the same fields (Spinward Marches: 327 KB, against about 116 KB compact without
it); v2 drops it. Anything the map needs from the generated tree is added here by name when a
slice needs it, never by copying the row. One function, `assembleSectorIndex` in
`packages/generation`, builds this document for both the local build and the Worker.

**Which sectors (decided 2026-10-03).** The truth is **every** M1105 sector in TravellerMap's
catalogue that has world data: 512 on 2026-10-03. Each carries its TravellerMap `tags` and a
`canonical` flag, true when tagged `OTU` or `ZCR` (the Official Traveller Universe plus the
Zhodani Core Route) and not `Apocryphal`, `Alternate` or `Unofficial`; 399 are canonical.
The rest are separate settings (Distant Fringe, Faraway, Orion OB1) and alternate versions
(the Judges Guild sectors), some of which share coordinates with canonical sectors. The
viewer draws the canonical layer by default and lets a reader pick an alternate; packages
may be built from any of them. `tools/truth/fetch_inputs.js` writes `universe/raw/sectors.json`
(slug, name, abbreviation, x, y, tags, canonical per sector), uploaded with the inputs as
`inputs/<version>/sectors.json`, which is what the build job reads for sector names,
coordinates and flags. Slugs are the sector name; when two sectors share a name (several are
"Unnamed") the slug gains the coordinates, e.g. `Unnamed_n15_1`. Each sector index and the
manifest carry `tags` and `canonical`.

**Where homebrew lives (decided 2026-10-03).** Every named sector in TravellerMap's catalogue
sits inside x ∈ [−200, 247], y ∈ [−248, 77]. The band **y ≥ 100** is the Homebrew Expanse:
no chart sector is there, so a builder's own sectors never overlap a real one. Rules:

- An own-map universe (`truth_version = null`) places its first sector at (0, 100) and each
  further sector at the next free x in the same row unless the builder moves it; a
  truth-pinned universe may add own sectors only inside the band.
- Own sector slugs are namespaced by the owner's handle with a tilde: `johnny~Sandbox_Alpha`.
  Canonical slugs never contain `~`, so an own sector can never collide with a chart sector by
  key, and two builders' sectors never collide by key because handles are unique. Hex keys are
  still `<sector_slug>/<hhhh>`.
- A package made from own sectors carries their slugs and band coordinates. Installing it
  into another universe keeps both. Two packages that chose the same band coordinates
  conflict by position; slice 4 reports that and the installer picks which to keep; moving a
  sector is the deferred relocation feature.
- The band is open-ended downward and sideways; there is no allocation registry. Builders
  who want to be sure of a private corner pick a distinctive y row.

**Unknown UWP digits (decided 2026-10-03).** TravellerMap writes `?` for a digit the chart
does not know; 24,090 of 180,312 rows carry at least one (15,984 fully unknown, 8,106
partial, mostly Zhodani Core Route survey rows with physical digits known and social ones
not). The legacy importer decoded `?` as zero and generated worlds from it, which is wrong
data. The truth does not: the parser keeps the raw `uwp` string, sets each numeric field to
`null` where its digit is `?`, and sets `partial: 'full' | 'partial' | null`. The build job
**does not generate a tree** for a partial row; its index entry carries the raw UWP and the
flag, and the viewer shows it as an incomplete survey. Filling unknown digits is a rules
question (which edition's table completes a missing population?) raised as Halt & Challenge
for a later slice; it is never done silently.

The sector's TravellerMap metadata XML is parsed at build time into `metadata`; raw XML is
not shipped. A truth build is a `truth-build` job (`architecture.md` §5): per sector, generate
at the pinned seed and settings, hash, write only new objects, write the index; then the
manifest, the `truth_versions` row and the `truth_systems` search rows. Accepted proposals (§8)
are applied by pointing their hexes at the proposal's objects instead of the generated ones.

## 6. The overlay document v3 (export file and import body)

Unchanged in shape from `persistence_v2.md` §2.1, owned by `packages/shared` as `OverlayDoc`:

- `base` is `null | { milieu, truthVersion, engineVersion, sectors: [{ slug, x, y }] }`.
- `hexes[hexKey]` is a `HexState` with the tree inlined (the file is self-contained) or a
  tombstone `{ deleted: true, rev, updatedAt }`.
- Hex keys are `"<slug>/<hhhh>"`. The legacy importer module (`packages/shared/legacy.ts`)
  translates the legacy `"<sectorNum>-<subsectorLetter>-<hhhh>"` ids using the file's grid and
  sector names and upgrades v1 and v2 files; it has its own fixtures (a v0.13 map, a v0.18 map,
  a v3 overlay).

Export assembles it from rows and objects; import hashes every inlined tree server-side, writes
objects, then pointer rows in one transaction, with a snapshot first. Files over 8 MB are
accepted gzipped; there is no multipart split.

## 7. Package manifest and content

`packages/<packageId>/<version>/manifest.json`
```json
{ "format": "voyage-package", "schemaVersion": 1, "packageId": "...", "version": 2,
  "kind": "subsector", "title": "...", "author": { "id": "...", "handle": "..." },
  "edition": "MgT2E", "engineVersion": "1.2.0", "truthVersion": "v1",
  "hexes": { "Spinward_Marches/1910": { "baseHash": "<truth tree hash or null>", "treeHash": "<hash>", "summary": { } },
             "Spinward_Marches/1912": { "baseHash": "…", "deleted": true } },
  "lists": { "routes": "<hash of the subset payload>", "borderPaths": "…" },
  "records": { "contentHash": "<hash of the records subset object>", "count": 3, "imageHashes": ["…"] },
  "publishedAt": "..." }
```

Publishing is a `publish` job: the Durable Object assembles the subset, objects are copied to
the public bucket, the manifest is written, `latest_version` is bumped. **Install** is a
three-way merge per hex against the target universe:

| Target hex currently | Result |
|---|---|
| equals `baseHash` (untouched truth, or an override whose `tree_hash` is `baseHash`) | fast-forward: write the pointer |
| equals `treeHash` | already installed: no-op |
| anything else | conflict: theirs / mine / per-field |

Installed rows carry `provenance: { packageId, version }`; records likewise.

## 8. Proposals and migration

- A proposal is `(packageId, version)` against `target_truth_version`. The reviewer's diff is
  the package manifest against the target's sector indexes: per hex, `baseHash` vs the truth's
  current `tree`, and `treeHash` vs `baseHash`. Accepted proposals are inputs to the next truth
  build (§5).
- **Migration** of a universe from truth v<N> to v<M>: for each override row, compare
  `base_hash` with v<M>'s `tree`. Equal: keep the row. Different and the row has no tree edit
  (`tree_hash` is null or equals `base_hash`): advance `base_hash`. Different and the tree was
  edited: list it for the builder (keep mine / take truth). Hash comparisons only; no tree is
  read until the builder opens a conflict.
